## 2. 調べてわかったこと

### 2.1 打刻の反映漏れ（依頼1）

**数字で見た現状**: 10月の勤怠181件のうち49件（27%）に【本人修正済】が付いている。修正履歴（EditLog）を見ると、9件は「退勤のときに出勤も同じ時刻で押され、あとで出勤時刻を直している」形（例: 東さん 10/3 出勤19:20・退勤19:20 → 出勤10:54 に修正。東さんは10月に5回）。つまり**朝の出勤がスプレッドシートに一度も届いていない**。また10/2には高橋さん10/1分の出勤09:40が空欄で上書きされて消えている記録がある。

打刻は基本的に**店舗のPCとタブレット（共用端末）**で行っている（chihiro 2026-11-08）。共用端末が2台あり、出勤と退勤を別の端末で押すことがあるため、「片方の端末が相手の打刻をまだ知らない」状態が起きやすい。さらに共用端末では次の事情が重なる。
- 打刻のたびに「ローカル更新後15秒は同期しない」保護が掛かり直す。出勤が続く時間帯はその端末の同期と再送が止まり続ける（再送は同期の中でしか動かないため）。
- タブレットは画面が消える・スリープすると、送信や再送が止まる。

原因は次の5つ（Aの「スマホを閉じる」は、共用端末では「タブレットのスリープ・送信中の通信切れ」に読み替え）。

| # | 原因 | どこ | 起きること |
|---|---|---|---|
| A | **送信の取りこぼし**。打刻は「送りっぱなし（no-cors）」で、届いたかを確認できない。さらに送信直後にスマホの画面を閉じたり別アプリに切り替えると、送信そのものが止まることがある（keepalive 指定なし）。それでも画面には「記録しました！」と出る | `sendToGAS` | 本人は押したつもり、クラウドには無い |
| B | **再送が遅く、しかも捨てられる**。未送信分の再送は「その端末で次にアプリを開いて、全件取得に成功したとき」だけ。次に開くのが翌日だと、その間に別端末で退勤が押されて新しい時刻の行ができており、サーバーは「古いデータ」として再送分を捨てる。端末側も「クラウドの方が新しい」と見て未送信リストから消す | `retrySendPending`・`writeRecord` の新旧判定 | 朝の出勤が永久に消える |
| C | **1日分の行をまるごと上書き**。打刻のたびに1日分の全項目（出勤・退勤・賄い・備考…）を送り、サーバーはそのまま行を書き換える。退勤を押した端末が出勤をまだ受け取っていないと、「出勤＝空」で上書きする | `handlePunch`・`writeRecord` | 出勤時刻が消える（10/1高橋さんの例） |
| D | **サーバーの負荷**。開いている全端末が3秒ごとに「全期間・全スタッフ（いま133シート）」を取りに行く。打刻があるたびに一時保存（キャッシュ）が消え、作り直しに5〜6秒以上かかる。打刻の書き込みは「順番待ち10秒」を超えると失敗するが、no-corsのため誰も気づけない | `doGet getAll`・`doPost` のロック | 人が重なると待たされる・失敗する |
| E | 修正履歴が毎回「出勤 09:57→09:57:00」のような**書式違いだけで記録**される（EditLogの大半がこれ）。退勤時に**備考が二重になる**（「【本人修正済】 / 【本人修正済】」「4310 ９月分の交通費 / 4310 ９月分の交通費」）。退勤時、入力欄に既にある備考に、同じ備考をもう一度つなげているため | `logEditIfChanged`・`handlePunch` の備考処理 | 履歴が読めない、処理が遅くなる、Excelの備考が汚れる |

### 2.2 出力が1回で揃わない（依頼2-1）

11/7の調査どおり。出力ボタンは同期を呼ぶが、Excelは「押した瞬間に画面が持っていたデータ」で作る。同期が実行中・ローカル更新直後15秒は「成功」扱いでスキップされる。さらに同期結果を返す変数（`finalMerged`）はReactの更新処理の中で埋めているため、空のまま返ることがある。

### 2.3 「本人確認：未」（依頼2-2）

**ボタンは動いていて、記録もされている**（Confirmations シートに29件）。原因は保存の形:
- GASが対象月を `"2026-10"` という文字で書き込むと、スプレッドシートが**自動で日付（2026/10/01）に変換**してしまう。29行すべてが日付になっている。
- 読み出すときは「スタッフ名|2026-10」で探すが、実際は「スタッフ名|Thu Oct 01 2026 00:00:00 GMT+0900…」になっていて一致しない → 全員「未」。
- 同じ理由で「押し直したら上書き」も効かず、同じ月の行が増えている（小田さんなど）。

### 2.4 シートの見た目の違い（依頼2-3）

- 新しい人（東さん・杉坂さん・西尾さん）のシートは、テンプレート内の「マスタ」シートをコピーして作っている。マスタには**有給欄の罫線・セル結合・賄い列の書式などが無い**ため、草野さんのシートと見た目が違う（10月出力で確認: 西尾さんは有給欄の枠なし、残有休日数のセル結合なし、賄い「1」の位置ずれ、休憩0:00表示など）。
- テンプレート内の既存スタッフのシートもそれぞれ少しずつ違う（小出さん・山田さんなどは有給欄が無いのを後から書き足している、林さんだけ「オンライン業務」欄があり、有給欄と重なっている）。

### 2.5 有給の表示（依頼2-4）

- 有給管理簿は「設定」シートの**現在日＝今日（TODAY）**を基準に、残日数（N列）・次回付与日（I列）を計算している。アプリは出力した日にこの値を読むので、**出力日の値**になる。
- 例: 高橋さんは 11/1 に付与。10月分を11月に出力すると、残日数に11/1付与分が足され、次回発生も 2027.11.1 になる（10月末時点なら 2026.11.1 が正しい）。
- ほかに見つけた危険: ファイル探しが「名前に『年次有給休暇管理簿2026』を含む」なので、同じフォルダの「年次有給休暇管理簿**2026旧**」を拾う可能性がある。また管理簿の年度は5/1〜翌4/30なのに、アプリは対象月の「暦の年」でファイルを選ぶため、2027年1〜4月分で別の年度のファイルを読む。

## 3. 直し方（改訂第3版: 第2回レビューを反映し、仕組みを簡単にした）

第2回レビューで、「古いアプリとの両立」「共通の更新時刻」「有給計算用のファイル作成」が複雑さと危険のもとだと分かった。第3版では次の3つの割り切りで単純にする。
- **古いアプリは使えなくする**: 打刻する端末は店舗PCとタブレットの2台だけなので、反映日にその2台を再読み込みすれば全端末が新しい版になる。GASは新しい版の印（`clientVersion`）が無い書き込みを受け付けない（6章の手順で、反映前に2台の未送信を0件にしておく）。
- **項目ごとに更新時刻を持つ**（共通の1つの時刻はやめる）。
- **有給の月末計算はファイルを作らない**（タイムカードのスプレッドシートの中に一時シートを作る。ドライブの権限は今のまま）。

### 3.1 打刻を確実に保存する（原因A・B・C）

**(1) 送る単位を「操作」にする**
- 端末の未送信リストは**操作ごとに1件**: `{opId, type, staffName, date, at（操作した時刻）, data, sentAt}`。
  - `type=punch`（打刻ボタン）: `data = {field: 出勤/中抜け開始/中抜け終了/退勤 のどれか, time, attrs}`。`attrs` には**その画面で本人が触った項目だけ**を入れる（今もある「触ったか」の印 isMealDirty・isTransportDirty・isRemarksDirty を使う）。退勤では休憩分数を必ず入れる（0 も 0）。触っていない賄い・交通費・備考は送らない＝消さない。
  - `type=edit`（履歴画面・管理者の修正、有給申請・取消）: `data = 修正後の1日分`。
  - `type=delete`（完全削除）、`type=confirm`（本人確認）。
- 今の打刻処理は送るデータをReactの更新処理の中で作っていて、「記録しました」と出ても送られないことがある（timecard.html 2235〜2270行付近）。**送るデータは更新処理の外で先に作る**。
- 端末に残っている古い形式の未送信（1日分まるごと）は、起動時に `type=edit`（削除フラグ付きは `type=delete`）に変換する。ただし6章の手順で反映前に0件にするので、通常は発生しない。

**(2) サーバーの書き込みルール（項目ごとの更新時刻）**
- 行ごとに17列目へ「項目ごとの最終更新時刻」を JSON で持つ（例 `{"clockIn":"…","meal":"…","remarks":"…"}`）。項目は 出勤・中抜け開始・中抜け終了・退勤・賄い・交通費・備考・休憩分数・有給・削除。
- `punch`:
  1. 行が削除済み、または有給なら書かない（`skipped`）。
  2. 時刻欄は「空」かつ「その欄の最終更新時刻より操作が新しい」ときだけ書く。既にある時刻は変えない。修正画面で消した時刻は、その消した時刻が記録されているので、それより前に押された古い打刻では戻らない。
  3. attrs の各項目は「その項目の最終更新時刻より操作が新しい」ときだけ書く（0・なし・空もそのまま）。項目ごとに比べるので、備考の修正が休憩分数を捨てる、といった巻き込みは起きない。
- `edit`: 送られた1日分のうち、**その項目の最終更新時刻より操作が新しい項目だけ**を書く（遅れて届いた古い修正で新しい打刻を消さない）。書いた項目の時刻を更新する。有給申請・取消もこれ。
- `delete`: 削除フラグと時刻を記録（今どおり行は残す）。それより古い操作は以後すべて `skipped`。
- `confirm`: 3.3-2 のとおり。
- 書き込んだ操作には送信元（店舗PC/タブレット）を15列目に残す。16列目は使わない（予備）。
- 同じ opId は何度届いても同じ結果（時刻比較のため）。GASは返事に「opIdごとの結果（applied/skipped）」を入れる。
- `clientVersion` の無い書き込み（古いアプリ）は `status:'error', message:'old_client'` で断る。

**(3) 列の追加**: 書き込み時に列が足りないシートは17列まで広げる（今は14列までしか広げない）。読み込みは17列まで（無い列は空扱い）。

**(4) 届いたかの確認と再送**
- no-cors をやめて GAS の返事を読む（`keepalive: true` 付き）。判定は HTTP ではなく返事の中身（順番待ち超えでも200で `status:'error'` が返るため）。返事で `applied/skipped` と返った opId だけ未送信リストから消す。
- 返事が読めない端末のための予備確認: 全件取得の返事に「各行の項目ごとの最終更新時刻」も入れ、**操作ごとに**「該当項目の更新時刻がその操作以降、または行が削除・有給」なら消す。
- 再送は全件取得と切り離し「起動時・画面に戻ったとき・20秒ごと」。15秒保護の対象外。送信中（送って30秒以内）の操作は再送しない（二重送信を避ける）。1回に送る量は**実際の大きさで 50KB 未満**に区切る。
- 打刻画面に「⚠ 未送信 n件」を表示（再送できたら消える）。
- もう一方の共用端末の打刻を早く知るため、名前を選んだ時点で、その人のその日の行だけを GAS から取る（`getRecord`）。**打刻ボタンは待たせない**（結果が間に合えば「すでに出勤済み」等の判定に使い、間に合わなくても(2)のルールで安全に合流する）。

### 3.2 待ち時間を減らす（原因D・E）

1. **全件取得を直近2か月分に絞る**（`getAll?months=2`）。古い月の履歴画面・出力は `month=YYYYMM` で取る。対象外の月の手元データは消さない。
   - サーバーの一時保存（キャッシュ）は範囲ごとの名前に「**世代番号**」を付ける。書き込みのたびに世代番号を1つ進める。読み込みは開始時の世代番号を覚え、終わったときに番号が変わっていたら**保存しない**（打刻前に始まった読み込みが古い結果を保存し直すのを防ぐ）。
   - 読めなかったシートがあれば返事に入れる（今は黙って成功を返している: gas_backup.gs 204〜209行）。
2. 自動同期 3秒→10秒、画面が裏のときは止める。15秒・8秒の保護の値は変えない。
3. EditLog は時刻を「時:分」にそろえて比べ、変わったときだけ記録。
4. 退勤時の備考の二重化を止める（入力欄の内容で置き換え）。既に二重のものは Excel 出力時にまとめる（元データは変えない）。

### 3.3 エクセル出力（依頼2-1〜2-3）

1. **出力は対象月をクラウドから直接取って作る**: 未送信を送り切る → `getAll month=対象月`・設定（名簿・本人確認）・有給 を取得 → 取得したデータそのものでExcelを作る。
   - **止める条件（統一）**: 勤怠データ・名簿・本人確認のどれかが取れない、または読めないシートがある → 出力しない（理由を表示）。有給だけが取れない → 出力は続け、有給欄に「取得できず」と書き、画面でも知らせる。
   - Excel の有給欄の近くに**基準日**（例「有給は 2026/10/31 時点」）を書く。
2. **本人確認**: 対象月・確認日時のセルを先に「書式なしテキスト」にしてから書く。読むときは日付になっている既存行を日本時間で「YYYY-MM」に直す。同じ人・同じ月が複数あれば最後の日時。押し直しは同じ行を上書き。確認ボタンは未送信リスト経由で届くまで再送。
3. **レイアウト統一（全員を草野さんの形に）**:
   - テンプレートを作り直す: 「マスタ」を**草野久美子シートと完全に同じ形**（列幅・行の高さ・罫線・結合・書式・条件付き書式・印刷設定・数式・シート全体の設定）にしてデータ欄を空にし、**他のスタッフ用シートはテンプレートから削除**する（同じ名前のシートがぶつからないように）。作り直しは手元（Python）で行い、草野さんのシートと自動比較して一致を確認する。
   - 出力時は全スタッフのシートをマスタから複製して作る（ExcelJSに公式の丸ごと複製は無いため、シートの設計図 `model` を写して名前だけ変える）。最後にマスタは今どおり残す。
   - **自動検査**（出力したファイルを Python で開いて確かめる）: 全シートの列幅・行の高さ・罫線・結合・書式・条件付き書式・印刷設定・数式・シート全体の設定（標準の行の高さ・行ごとの書式・表示倍率・既定の文字）がマスタと同じ。1枚のシートを書き換えても他のシートが変わらない（複製が独立している）。LibreOffice で再計算した合計（日数・勤務時間・交通費・賄い・オンライン業務）が試験データからの期待値と一致。草野さんと新人のシートを画像にして並べ、目でも確認（10月出力の西尾さんは、行の高さの数値は同じでもシート全体の設定と有給欄の罫線・結合が欠けて「スカスカ」に見えていた）。
   - **オンライン業務欄（chihiro指示 2026-11-08）**: 有給欄は全員同じ位置（A33〜E34）。その下に別枠「オンライン業務」。対象月の備考に「オンライン」を含む日があるスタッフだけに出す（今は林さん。毎月ある）。
     - A36「オンライン業務」、37行目から1件1行で C=日付（m/d）・D=備考の文言（【本人修正済】は除く）・E=金額、最後の行の次に「合計」＝その全行の SUM。**件数に上限は設けず、件数分だけ下に伸ばす**（A〜E列はその下が空いている）。罫線は有給欄と同じ細線。マスタの C36:D36 の結合は外す。
     - 金額は備考の「数字（カンマ可）＋円」を拾う（例: オンライン作業代21,565円 → 21565）。拾えないときは E を空欄にして文言だけ転記し、その行に「金額要確認」と書く（推測で埋めない）。
     - 備考欄の元の記載は残す。林さんの過去6か月の記載はすべて拾える。
   - 出勤記録の無いスタッフのシートは出さない。外注用の出力は今回触らない。

### 3.4 有給を「対象月の末日時点」で出す（依頼2-4、chihiro選択 2026-11-08）

管理簿の原本は今までどおり「今日」基準（スタッフに今の残日数を答える用）。Excel に出す値だけ月末時点で計算する。

**方法（改訂: 新しいファイルを作らない・権限を広げない）**
1. 出力時、GAS はスクリプト全体の順番待ち（ロック）を取り、同時に1つしか動かないようにする。
2. 管理簿の「設定」→「スタッフ名簿」→「管理簿」の順に、**タイムカードのスプレッドシートの中へ**シートごとコピー（`copyTo`）し、元と同じ名前に付け直す（参照先が先にある順番でコピーする）。管理簿の原本は読むだけ。これらの名前は「スタッフ名_年月」の形ではないので、打刻データの読み込みには混ざらない。
3. コピーした「設定」C5（現在日）を対象月の末日にし、計算を確定させて（`flush`）、残日数（N列）・次回付与日（I列）を読む。`#REF!` などのエラーがあれば月末値は使わない。
4. 読み終わったら3枚のシートを削除する（「最後に必ず実行」の形）。実行前に、同じ名前の残骸シートがあれば先に消す（ロック中なので他の出力の物を消すことはない）。
- 権限は今のまま（スプレッドシート・ドライブ読み取り）。ファイルの作成・削除はしない。

4. **EditLog の重複・抜けを防ぐ**: EditLog の各行に opId を入れる。書く順番は「OpLog 受付（flush）→ 勤怠の行と EditLog を同じ手順で書く（flush）→ OpLog 完了（flush）」。「受付」のまま止まった opId を当て直すときは、EditLog の直近500行にその opId があれば EditLog は書かない（勤怠の行は同じ結果になるので書き直してよい）。今のコードの「EditLog を先に足してから勤怠を書く」（gas_backup.gs 574・580行）はこの順番に改める。
5. **出力前に2台の未送信を確かめる（3.7-7 に追加）**: 各端末は同期のたびに「端末名と未送信の件数」を GAS に知らせる（端末名は管理画面で「店舗PC」「タブレット」と1回だけ付ける）。Excel 出力（通常・外注）の前に、直近30分以内に知らせのあった全端末が「未送信0件」かを表示し、0件でない端末があれば「タブレットに未送信が2件あります。タブレットを開いて送信されるのを待ってから出力してください」と止める（管理者が分かったうえで続ける選択肢も残す）。
6. **細かい点**: 3.10-6 の判定変更に合わせ、「新→古→新」の往復試験に「遅れて届いた打刻を新しい版が保存した行」が古い版の行と誤判定されないことを加える。

## 7. 確かめ方

- **手元の自動テスト**（GASのコードを Node で動かし、スプレッドシート部分だけまねる＋Playwright で画面）
  - 通信断で出勤→退勤 → 2件残り、復旧後に両方届く。送信中は再送しない。
  - 端末Aで出勤、端末Bが知らないまま退勤 → 出勤が消えない。Bで触っていない交通費・備考・賄いも消えない。
  - 修正画面で出勤を消した後、古い出勤が遅れて届く → 戻らない。修正した備考・休憩分数も古い打刻で戻らない。削除済み・有給の日には書かれない。
  - 休憩0分・賄いなしを明示 → そのまま（45分に化けない）。
  - `status:error` の返事 → 未送信のまま再送。古いアプリ形式の書き込み → 断られる。
  - 読み込み中に打刻 → 古い結果がキャッシュに残らない。
  - 出力1回で対象月が全員揃う（手元が古くても）。読めないシートがあれば止まる。有給だけ失敗なら「取得できず」で出る。
  - 本人確認が「本人確認済み: 日時」で出る（日付に化けた既存行も拾える）。
  - 3.3-3 の Excel 自動検査一式。オンライン業務が6件ある場合も合計が全件分。
- **実際の GAS で**（本番の前に、控えのコピーにつないだテスト用デプロイで）: 各命令、本人確認、有給の月末計算（3.4 の3人照合）。
- **店舗の実機で**（合格条件）: タブレットで出勤→PCで退勤して両方残る／タブレットの Wi-Fi を切って打刻→「未送信1件」→ Wi-Fi を戻して20秒以内に消える／2人続けて打刻しても待たされない／出力1回で揃う。

## 8. 危険

- GAS の返事を読む送信が一部の端末で動かない → 予備確認が残るので今より悪くならない。
- 有給の月末計算が正しく出ない → 3.4 のとおり切り替えて相談。
- 反映直後に古い版のままの端末があると打刻が断られる → 6章2で2台をすぐ再読み込み。断られた打刻はその端末の未送信に残り、新しい版で送られる。
